# フリーランス手取りシミュレータ — データ設計

Cloudflare D1 (SQLite) 前提。Worker から書き込み、GitHub Pages 側の単一 HTML から fetch。

---

## 1. 設計の原則

### 原則1：統計用とユーザー保存用を物理的に分ける

| テーブル群 | 目的 | 個人との紐付け |
|---|---|---|
| `simulations` / `cta_events` | 独自調査・記事・特単交渉の材料 | **なし**（一切持たない） |
| `accounts` / `snapshots` | リスト化・再訪・申告シーズンの送客 | あり |

同じデータを二重に持つことになるが、目的が違うので許容する。混ぜると統計を公開できなくなる。

### 原則2：金額は丸めて保存する

売上・経費は **10万円単位に切り捨て**て保存する。

- 統計の精度は 10万円刻みで十分（中央値・分布を出すだけ）
- 生の金額 + 職種 + 都道府県 + 稼働年数 が揃うと個人が特定されうる
- 丸めておけば「匿名加工情報」としての説明が容易になる

計算結果の表示は生値で行い、**保存する瞬間だけ丸める**。

### 原則3：追記のみ（UPDATE / DELETE しない）

`simulations` は追記専用。同じ人が入力し直しても新しい行が増えるだけ。

- 「入力し直した回数」自体がツールの改善データになる
- 時系列で見たとき、過去を書き換えていないことが保証される
- 重複除去は集計クエリ側で `session_hash` を使って行う

### 原則4：同意がない行は入れない

`consent_stats` にチェックがない場合、`simulations` には**書き込まない**。計算結果は普通に表示する。同意率は 7〜8 割程度を見込む。

## 2. 収集フィールドの意図

「なんとなく集める」項目はゼロにする。各フィールドが、①記事のネタ、②出口の出し分け、③特単交渉の材料、のどれかに必ず紐づく。

| フィールド | 何に使うか |
|---|---|
| `occupation` | 職種別ページの自動生成。横展開の軸 |
| `work_style` | 「面貸し vs 業務委託」の実測比較記事 |
| `commission_rate` | **最重要**。求人票の建前と実測値の乖離を出せる。他媒体が絶対に持てない数字 |
| `revenue_yen` / `expense_yen` | 職種別の経費率中央値。記事の主役 |
| `filing_type` | 白色の割合 → 会計ソフト案件の訴求根拠 |
| `invoice_registered` | 制度変更のたびに需要が跳ねる。定点観測すると価値が出る |
| `uses_accounting_saas` | **未導入者だけに出口を出す**ための判定。導入済みに広告を出しても無駄 |
| `uses_tax_accountant` | 「売上1000万超で税理士なし」層 = 税理士紹介の最有力ターゲット |
| `health_insurance` | 国保 vs 社保の手取り差。検索需要が大きい |
| `entry_source` | `partner:xxxx` 形式で BtoB 提供先ごとの成果を分離できる |

`uses_accounting_saas` と `uses_tax_accountant` の2つが、収益設計上いちばん効く。ここで「まだ使っていない人」を判別できるので、無駄な広告表示が消える。

## 3. セグメントと出口

| セグメント | 条件（目安） | 主な出口 |
|---|---|---|
| `starter` | 売上300万未満 | 会計ソフト（青色申告）、事業用カード |
| `growth` | 売上300〜800万 | 会計ソフト、小規模企業共済、iDeCo |
| `taxable` | 売上1000万超 or インボイス登録済 | 税理士紹介、インボイス対応ソフト |
| `high` | 課税所得900万超 | 税理士紹介、法人成り相談 |
| `cashflow_watch` | 経費率が高く手元が薄い | **後述の注意あり** |

### cashflow_watch の扱いについて

資金繰りが厳しい層に**ファクタリングを出すのは推奨しない**。手数料が実質年率で見ると非常に高く、一度使うと資金繰りがさらに悪化する構造がある。単価が高いので誘惑はあるが、ユーザーを壊す出口はリストごと失う。

このセグメントには、日本政策金融公庫の創業融資・制度融資を先に出し、必要なら民間の低利な選択肢を並べる。長期的な信頼のほうが、単発の高単価より収益が大きい。

## 4. 表示上の免責（税理士法対応）

税理士法52条により、無資格者による個別具体の税務相談は禁止されている。ツールの出力は必ず次の形にする。

- ⭕️ 「一般的な計算式に基づく概算です」「◯◯控除の対象となる可能性があります」
- ❌ 「あなたは◯◯控除を適用できます」「この方法で節税してください」

一般的な計算の提示はセーフ、個別の判断を下すとアウト。この免責文の直後が、税理士紹介への最も自然な導線になる。

## 5. プライバシーポリシーに書くこと

1. 入力内容を個人が特定できない形に加工したうえで統計利用すること
2. 統計結果をサイト上で公開する場合があること
3. 同意しなくても計算機能はすべて利用できること
4. メールアドレスを登録した場合の利用範囲と、配信停止の方法

3 を明記しておくと、同意取得の適法性が安定する。

## 6. 最初にやること

**匿名データの保存だけは、公開初日から動かす。** 他の機能は後から足せるが、保存し忘れた期間のデータは二度と手に入らない。

順番：

1. `simulations` への書き込み（初日）
2. `cta_events` の記録（初日〜1週間）
3. `accounts` / `snapshots`（3〜6ヶ月目、リスト化を始めるとき）
4. 300件たまった時点で第1号の独自調査記事
